## Architecture
- Layers: `src/domain` (pure poker types/rules), `src/strategy` (engine + providers + range data), `src/generator` (seeded scenarios), `src/components` + `src/routes` (UI only). Why: UI never decides Raise/Fold; rules stay testable and swappable.
- All decisions go through `strategyEngine.decide(scenario)`; new sources (solver, ICM, PKO) are added as `StrategyProvider`s in priority order. Why: one entry point, pluggable sources.
- Ranges are serializable `RangeDefinition` objects (hand → frequency, with source + version). Why: future JSON/CSV/API import.
- Scenarios are generated from a seed via a deterministic RNG and identified by `scenarioId` encoding context + seed. Why: any exercise can be reproduced.
- `src/playback` is a framework-free hand replay (timeline from `TableState.actions`, table view, timer, `HandPlaybackController` state machine); `src/hooks/use-hand-playback.ts` only adds timing/sounds. Why: playback gating is testable and never touches strategy.
- Tournament/bounty/chip data stays null unless real data is configured; null data must never feed the engine. Exception: ICM stages carry a model payout structure with `source: "model"`, always labelled in the UI. Why: no invented numbers presented as real.
- `src/sessions` owns framework-free session configuration, lifecycle, records and summaries; UI orchestrates playback and passes outcomes into it. Why: completion and filter consistency remain independently testable.
- Session scenarios use position/context-aware versioned IDs while legacy IDs remain reproducible. Why: filters and explicit strategic contexts must not break scenario replay.
- Session availability is gated before the engine, and approximated references require explicit acceptance; unsupported ICM, bounty and non-open spots stay unavailable. Why: preserve engine compatibility without implying nonexistent specialist strategies.
- `MultiTableController` owns deterministic hand allocation and one independent `HandPlaybackController` per table; React hooks only drive each clock. Why: simultaneous decisions and global completion remain testable without React.
- Global hand targets cap allocated scenarios, not per-table targets; only completed outcomes become records. Why: concurrent responses cannot overshoot completion or count unfinished hands.
- `SessionResultEngine` consolidates actual records, mixed status, sizing and directional action differences without inferred strategic causes. Why: reports stay factual and future baselines need real samples.
- Explicit strategic contexts must match a provider's returned range context, and optional bet sizes come only from strategy data. Why: prevent cross-context fallback and invented sizing.
- Multitable controls are table-local and do not register global action hotkeys. Why: one key must never answer multiple pending decisions.
- Reference open ranges come from a hand-authored 169-hand priority list (`OPEN_PRIORITY`) cut at a per-context %; only the boundary hand is fractional. Why: realistic nested ranges and genuine mixed spots without inventing solver data.
- `summarize().hits` includes valid mixes; `mixed` is a subset. History/evolution must never add them together. Why: avoid inflated accuracy.
- Borderline hand focus re-rolls the seed deterministically instead of forcing a hand, so every scenario stays reproducible from its `scenarioId`. Why: replay and sharing keep working.
- Replay sessions (`config.replay`) reuse recorded `scenarioId`s and override filters/goal via `targetHands()`. Why: "refazer erros" reproduces the exact spots.
- Components that run timers must not depend on parent callbacks recreated each render; keep them in refs. Why: the session page re-renders every 100 ms.
- Push/fold strategy is computed, never hard-coded: `strategy/equity` (generated equity data, see `scripts/`) + `strategy/pushfold/nash.ts` solver + `providers/push-fold.ts`. Model limits must be shown to the user. Overcalls: one overcall strategy per seat, max three players all-in, exact side pots/bounties, three-way equity from heads-up equities via `share3` (fitted Bradley–Terry, RMSE ~1.7 pts vs Monte Carlo). Why: real numbers only.
- Non-open-raise spots use v5 scenario IDs that encode spot, hero and shover, and always consume their RNG draws. Why: an ID built with or without explicit positions must replay identically.
- Stack buckets are spot-specific (`spotStacks`): open raise 100/40/25/15, push/fold 15/12/10/8/5. Why: no open-raise advice at 5bb, no push/fold advice at 100bb.
- ICM stages (pre_itm, bubble, ft) always solve with table ICM; every trainable spot has an ICM strategy (regular and PKO; bounty via the ICM engine in pko_icm). `LEGACY_STAGES` keeps old random contexts reproducible. Why: no chip-EV advice disguised as ICM.
- Evolution/leaks read only the local decision log written when a session ends (`sessions/decision-log.ts`); leak analysis (`sessions/leaks.ts`) reports rates, sample sizes and error direction only. Why: no invented causes; one source of truth for history.
- PKO is solved only together with ICM (mode `pko_icm`): bounty money and payouts share one currency; model bounties derive from the starting bounty (`FIRST_PRIZE_IN_STARTING_BOUNTIES`) unless the session provides a real one. Why: avoid an arbitrary $→chip conversion.
- PKO model (`domain/pko.ts`): each player has an accumulated head (`sampleHeads`: Poisson KOs weighted by stack, half of each eliminated head added) in starting bounties, drawn after the cards for every PKO spot. Bounty power BP = heads in starting bounties ÷ stack in starting stacks; the team's BP → equity drop table (`BP_EQUITY_DROP_TABLE`, approximations) is embedded and shown on seats, the tournament panel and explanations. Early/mid (mode `pko` for push/fold) converts a KO into chips with `PKO_BOUNTY_CHIP_VALUE` = 0.27 starting stacks per starting bounty, calibrated so call thresholds reproduce the table (±1.5 pt, tested); the old 0.5 overvalued bounties (8–9% drop at BP 1 vs 5.5%). Sessions may set the tournament (`pkoSetup`: buy-in, bounty share, starting stack chips, current BB chips → starting stack in BB and starting bounty money); `pkoStartStackBb` stays for old configs. Non-push PKO spots at 25bb would use the solver presets pkochip_25 / pkomid_25 chosen by the BP of the aggressor, but both are switched off (`PKO_CHIP_PRESETS_ENABLED = false`, audit 2026-10-25: pkochip uses the old 0.5 convention, BP ≈ 2.4 equivalent, and opens 95%; pkomid did not converge) until the solver delivers BP-based presets. Why: ranges move with bounty power, not with covering alone.
- Real-hand import lives in `src/import` (pure parser + analyzer, fixtures in `src/test/fixtures`). The Suprema API only answers its own replayer, so the browser fetch goes through the `fetchSupremaReplay` server function (`src/fetchers/suprema.ts`; a `src/server` folder breaks the Lovable build); the page also accepts pasted JSON. Why: keep analysis testable and the network edge isolated.
- Multiway hands use `strategy/multiway/simulate.ts` (Monte Carlo with side pots, ICM and bounties) against role-based, user-editable ranges. It is EV given assumptions, never labelled as equilibrium. Why: honest answers for spots the Nash solver does not cover.
- Multiway opponent defaults: 3bet % from a position table (`threeBetPct`), first-in all-ins from the real-table Nash solve, and calls of hero's shove by pot odds vs the range opponents assign to hero (editable `hero` assumption row). User overrides always win. Why: fewer arbitrary constants; every assumption visible and editable.
- Analyzed real hands are stored locally (`import/real-hand-history.ts`, key `nvt-real-hands-v1`, chip EV only) and shown in /analisar and in the Evolução "Mãos reais" section; they never mix into the training decision log. Why: real play and drills are different samples.
- Feedback "why" lives in `strategy/insight.ts` (pure): EVs come only from `StrategyDecision.actionEvs` (set by providers that compute EV, today Nash push/fold); the call break-even equity is fitted from the solver's EV line (EV(call) is linear in equity vs the shove range), so it already includes ICM/bounty. Reference open ranges show order/boundary only, never an EV. Why: every number in the feedback traces back to the same solution that graded the hand.
- Home has four doors (ready trainings, /analisar, /sessao, builder). Ready trainings are split into Pré-flop / Pós-flop tabs (`homeModuleGroups().postflop`; modules tagged `PÓS-FLOP` and `POSTFLOP_DRILLS`, which link to their own routes such as `/cbet`); the tab is remembered in `nvt-home-phase-v1`. Ready trainings start in one click when `configurationError` passes; the reference-acceptance is remembered in localStorage (`nvt-reference-accepted-v1`) after the first explicit acceptance. Why: fast start without silently skipping the acceptance rule.
- "Montar meu treino" (`sessions/custom-training.ts`) maps builder choices to a SessionConfig and only offers combinations `configurationError` accepts (ICM stages for every implemented spot, since each has an ICM strategy). Saved trainings live in `nvt-custom-trainings-v1`. Why: users can't build a session the engine can't answer.
- Session analysis (`import/session-analysis.ts`) reuses `analyzeHeroPreflop` per hand (chip EV); deep-stack first-in open/fold is checked against the reference open range and reported separately with no EV. Why: one analyzer for single hands and sessions; reference checks never pose as EV.
- Real-hand replay (`import/replay.ts`) rebuilds frames from ImportedHand (antes from everyone, blinds, per-action chip increments, street sweeps, runout, showdown); a test enforces chip conservation per frame. It reuses the trainer table look, never a poker site's layout. Why: exact, testable reproduction without copying third-party branding.
- Accounts (Lovable Cloud): every route except `/entrar` and `/redefinir-senha` is behind `AuthGate` (approved profile required). Sign-up is open, accounts start `pending`, only admins approve; roles live in `user_roles` checked by `has_role()`. Why: monetizable product with admin-controlled access and no self-promotion.
- localStorage stays the read model; `src/account/cloud.ts` pushes on session end / hand analysis and syncs both ways on login (owner key clears another user's local data). Modules used by tests never import the Supabase client. Why: offline-tolerant UI, multi-device history, testable logic.
- Team ranking comes only from `team_ranking_data` (aggregates of approved teammates, by nickname); rules live in `sessions/ranking.ts`. Why: privacy and one tested definition of the leaderboard.
- Team charts (`strategy/ranges/nvt-charts.ts`) are transcribed images; a test pins every chart whose legend printed percentages. `nvtTeamProvider` (before the reference provider) serves open raise from them; stack mapping of the open sets is an explicit, editable assumption (`NVT_OPEN_SET_STACKS`). PKO shove charts drive open_shove in PKO mode at 15bb via `pkoTeamProvider` (KO level = cash bounty in chips ÷ stack, bands in `koLevel`); SB limp chart is study only. Why: the team's own ranges are the reference, without guessing data the images don't show.
- Blind War limp spots: `limp` (SB first-in: fold/limp/raise/all_in) and `limp_call` (SB limped, BB iso to `BB_ISO_SIZE`: fold/call/all_in), 25bb only. Source since 26/10: HRC (`preflopSolverProvider`, family `hrc:<situação>`, validated) from the limp branch of the HRC 25bb exports already in `public/solver/hrc` (tree ALLOW_SB_COMPLETE: SB open 2bb, BB iso 3bb = `BB_ISO_SIZE`). `scripts/import-hrc.py` writes `limp` into each preset JSON (also BB vs limp and SB vs BB jam, unused yet); `scripts/build-hrc-limp.py` generates the synchronous `preflop-solver/hrc-limp.ts` (SB nodes, freq+EV) so the generator (deterministic by seed) and the provider never depend on a loaded file. Per hand the HRC frequency rules, unless it contradicts HRC's own EV by more than the gate margin (0.05bb / 0.02%): then the max-EV action (same 'read by HRC EV' rule as the Nash references). `limp_call` only deals hands HRC limps ≥ `MIN_LIMP_FREQ`. Without an HRC situation (PKO + ICM) the NVT SB 25bb chart answers (`sbLimpProvider`, calibrated ICM, never validated). `vs_limp` (BB vs the SB limp: check / iso to `BB_ISO_SIZE` / all_in, EV relative to check) comes only from HRC (`bbVsLimp` node); there is no fallback, so PKO formats are refused in `configurationError`. Why: the team chart is not a solver; HRC already solved the limp tree in the exports we validated.
- `SessionFilters.shovers` pins the aggressor (shover/opener) for spots with one; the extra RNG draw happens only when the filter is set. Why: Blind War BB trees (BB vs SB) without breaking old seeds.
- Open raise at ≤15bb (`OPEN_SHOVE_MAX_STACK`) offers fold/raise/all_in; `withOpenShove` (engine post-step, chip EV only) keeps the open source for raise and adds the table's Nash open-shove range for all-in, normalising displayed frequencies. No EV for raise, so `actionEvs` stays unset. Why: the theory's 15bb raise+shove mix without overriding the team chart.
- Imported-hand ICM uses the tournament phase typed by the user (`icmFieldMode`): off-table players are appended as non-acting seats (callers passed explicitly) so table ICM sees the bubble; field capped at `ICM_MAX_FIELD` (compressed proportionally, labelled). Why: replays carry no players-left/paid data, and table-only ICM erases the bubble.
- Training metrics (`sessions/metrics.ts`) and the coach panel (`sessions/coach.ts`, route `/time`) are pure functions over `DecisionLog`; `edge` (hand on the range boundary) is recorded per decision. Coach/admin read access comes only from RLS policies in `20261017230000_coach_panel.sql`; the app degrades (own data + notice; uploads retry without `edge`) when it is not applied. Why: one metric definition for player and coach, no schema lock-in.
- Reaction spots `vs_open` / `vs_3bet` (`providers/reaction.ts`) are an approximate reference, labelled as such: equity vs the aggressor range (opener = `openRangeFor`, 3bettor = polarized top-X% from `threeBetPct`) × realization by role/stack (`playability` per hand) vs pot odds; value/bluff 3bets and 4bets by equity rank and blocker score; ≤25bb all-in from the table Nash resteal solve. No `actionEvs` (no fake EV in metrics). `vs_3bet` re-deals until hero holds a hand from his own open range; its aggressor acts after hero (`aggressorPositions`). Why: trainable spots now, replaceable by team charts without changing the session layer.
- ICM lives in `src/icm/engine.ts` (pure): `icmValues` (exact ≤20 alive, pruned at the last paid place; seeded Monte Carlo above), `pairRisk`/`riskMatrix` (BF and RP = BF/(1+BF) − 50%), `fieldModel` (table + off-table players at avg stack; compression keeps the distance to the money near the bubble), `dealValues`. `domain/icm.icmEquity` re-exports `icmValues` so the solver and the multiway simulator share it. Why: one ICM implementation for trainer, analysis and the /icm calculator.
- ICM open/defense (`providers/icm-preflop.ts`, ICM branch of `reaction.ts`): calibrated reference, not solver. Open range = chip-EV source (team chart/reference composition kept) × exp(3.8 × risk advantage vs players behind, blinds weighted 1.5), clamped 0.4–1.8× and ≤75%. Vs open: opener range ICM-adjusted the same way, hero call threshold += 0.4 × RP vs opener, 3bet × max(0.35, 1 − 3·RP), ≤25bb all-in from the ICM Nash resteal solve compared with call EV converted bb→% by hero marginal chip value. Why: theory-consistent ICM spots without a postflop solver.
- ICM extensions (calibrated references, not solver): vs 3bet (3bettor range × exp(−3.8·RP_them + 1.5·RP_hero), hero call need += 0.4·RP, jam equity − RP, 4bet bluffs × (1 − 3·RP)); Blind War limp (raise share × exp(3.8 × advantage) over the NVT chart order, vs iso continuing range loses its weakest 2·RP, bounty discount adds best folds). `icmContext(s)` builds prizes + PKO heads for icm / pko_icm. ICM reaction decisions report source `icm` (or `pko` in pko_icm) instead of the chip-EV reference label. Presets: Vs Open com ICM (3bet/call/fold from every position), Defesa do BB com ICM, Vs 3Bet com ICM, Resteal com ICM.
- `SessionConfig.icmField` (remaining, paid, off-table avg, prizes) is applied by `withIcmField` on ICM stages: model payouts are replaced by `fieldModel` (maxField 14, exact) and off-table stacks go to `tournament.fieldOthers` (+ `fieldOtherBounty`); every ICM consumer appends them as non-acting seats (`icmStacks`, `pushFoldInputFromTable` with explicit callers). Not part of the scenarioId (like ftPayouts). Why: trainer ICM matches the user's real tournament instead of table-only ICM.
- Flop c-bet drill (`strategy/postflop/cbet.ts`, route `/cbet`) reads solver output only: `scripts/import-cbet-solver.mjs` converts `solver-data:trainer-export/*.json.gz` into `public/solver/cbet/<spot>.json` + `manifest.json` (lazy fetch, cache keyed by `version`). Two grading trees, both solver output (12 numbers per combo): `full` (default: check/33/65/pot with the full tree's EVs) or `simple` (check + the board's size). EV lost = max(EV) − EV(choice) in the chosen tree, loss < `MIX_TOLERANCE_BB` (0.02) is an accepted mix. Exports without `simple` (e.g. v2 with the solver-computed BB defence) import as full-tree-only (`size: null`, 8 numbers per combo, `trees: ["full"]`) and the drill hides the simple tree for that spot; `<spot>_v<N>` files replace `<spot>` (highest N wins) and each spot carries its own version/note in the manifest. Only sizes present in the solved tree are offered (no all-in/overbet until the solver tree has them); BB response is info only; range/nuts-advantage text is standard theory, labelled. It is a separate drill with its own history (`nvt-cbet-history-v1`), not a `TrainingScenario`, so it never enters the preflop decision log/replay. The page uses the same trainer table as preflop (`PokerTable` with the optional `board` prop; `strategy/postflop/cbet-table.ts` builds an 8-max TableState/TableView whose preflop actions sum to the solver pot: open = (pot − ante − SB)/2). Sync: `scripts/sync-solver-data.sh` (run every 3 h by a scheduled task) fetches `solver-data`, compares the `trainer-export/` tree with the commit recorded in `manifest.source.commit`, and only then re-imports every `<hero>_vs_<villain>_<stack>` export (open size from `config/spots.json`; non-drill formats skipped, vanished spots removed). The table derives positions and IP/OOP from the spot id, so new SRP spots need no code. Swapping data (e.g. BB defence solved) = rerun the script; validation rejects other `format`s. Why: real solver numbers, swappable files, no fake preflop scenario.
- Presence (admin "Online agora"): approved users send a heartbeat every 60 s, on route change, on tab visibility change and on leave (`account/presence-client.ts` → RPC `touch_presence`, security definer, migration `drizzle/migrations/0004_user_presence.sql`). The server stores last_seen, page, activity, visibility and accumulates today's visible time (gaps ≤ 3 min, day in America/Sao_Paulo). Status rules are pure (`account/presence.ts`: online < 150 s and visible, away = tab hidden, offline otherwise). Only the user, coaches and admins can read rows; nobody writes the table directly. The admin page polls every 30 s and degrades with a notice when the migration is missing. Why: honest "who is online" without trusting client clocks or exposing presence to other players.
- Preflop solver (`strategy/preflop-solver/catalog.ts` + `providers/preflop-solver.ts`, first after manual): the team's preflop engine catalog (`solver-data:preflop/catalog`, full-tree solve with postflop realization curves; 9-max fixed stacks: chip_25/40, pkochip_25 (BP≈1.3), pkomid_25 (BP≈0.58; PKO preset picked by bounty power), {preitm,bubble,ft}×{iguais,curtos_ini,curtos_fim}×{icm,pko}) imported by `scripts/import-preflop-solver.mjs` to `public/solver/preflop/` (also via `sync-solver-data.sh`). It answers vs_open, vs_3bet (only hands the solver opens) and open_raise in ICM/PKO, plus chip-EV open only where no team chart exists (SB); team charts keep chip-EV opens. Frequencies < `MIN_FREQ` (5%) are dropped and renormalized so solver noise is not a "valid mix"; `actionEvs` relative to fold in the catalog unit (bb or % prize pool). ICM spreads are matched to the nearest catalog stack distribution and labelled. The engine is synchronous, so sessions preload the presets their filters need (`preloadPreflopSolverFor` in `begin`); without a loaded preset the spot falls back to the previous source with its own label. Reaction-spot opens are 2bb at ≤40bb (100bb: 2.5bb) to match the solved tree; vs_open at 40bb and 25bb ICM/PKO/SB opens have an all-in button. Audit vs old sources: `docs/auditoria-ranges-solver.md`; validity audit (consistency, premises): `docs/auditoria-solver-2026-10-25.md`. SB open raise has no limp button: hands the engine limps go to the best-EV legal action instead of fold when raise/all-in beats fold. Why: equilibrium numbers replace approximate references wherever the solver has them.
- Near-indifferent hands: `strategyEngine.grade` accepts a non-recommended action as `ACCEPTABLE_MIXED_ACTION` when the source has `actionEvs` and the EV lost is below `EV_MIX_TOL_BB` (0.03bb) / `EV_MIX_TOL_PCT` (0.01% prize pool). Why: pure Nash/solver boundaries should not punish a 0.00bb choice (same idea as the c-bet tolerance).
- Hand reports ("Reportar esta mão", `components/reports/ReportHand.tsx` in the feedback and the compact feedback): approved players insert into `hand_reports` (migration `drizzle/migrations/0006_hand_reports.sql`, RLS: insert own, read own/coach/admin, update coach/admin, explicit GRANTs for the Data API). Rules are pure in `sessions/hand-reports.ts`. `HandReportsPanel` (in /admin and /time) groups reports by scenarioId, re-decides the hand today via `scenarioFromId` (+ solver preload) to show whether the answer changed, lets coach/admin mark "Trainer certo / Corrigida / Descartada" with a reply, and copies the open list for review in a Claude chat. Why: player feedback reaches whoever can verify it with the solver, without trusting intuition over numbers or ignoring real bugs.
- 3Bet size drill (`strategy/preflop-3bet/threebet.ts` + `threebet-table.ts`, route `/3bet`, Home pré-flop "Solver" group via `PREFLOP_DRILLS`) reads only the preflop engine's `solver-data:trainer-export/preflop-3bet/` (imported by `scripts/import-3bet-solver.mjs` into `public/solver/3bet/<hero>_vs_<opener>_<stack>.json`, all contexts per spot; also via `sync-solver-data.sh`). Actions fold/call/3bet s1/3bet s2/all-in with the engine's EV relative to fold; grading = EV lost with the trainer's `EV_MIX_TOL_BB`/`EV_MIX_TOL_PCT`. Contexts (chip, ICM presets, cobrindo/coberto ICM and PKO+ICM) come from the files, nothing else is offered. Separate history (`nvt-3bet-history-v1`), never in the decision log; sessions' vs_open still use the catalog's single 3bet size. Why: two-size 3bet training with real engine numbers without changing the session layer.
- Trilha NVT (`sessions/trail.ts`, `components/home/TrailPanel.tsx`, top of the Home): ready trainings grouped in 3 suggested levels (Fundamentos, Intermediário, Avançado = ICM; nothing is locked). A phase is a preset in 20-hand borderline sessions themed `Trilha · <phase>`; only those sessions count. Pass = last 40 decisions with ≥75% accuracy and avg EV loss ≤0.10bb (≤0.05% in pct; ignored when the source has no EV); stars 2 = 85%, 3 = 92% + EV ≤0.05bb; best window kept. Level prova / leveling test = 40 borderline scenarios drawn across the level's phases, played as a replay themed `Prova · <level>`, pass 80%; a level is completed by the prova or by passing every phase. Progress is derived from the existing session history + decision log (synced with the account); nothing new is stored. c-bet and 3bet-size drills are bonus phases (not graded: provisional data / separate history). Thresholds are a first proposal to calibrate with usage. Why: give players a path and a reason to come back, using data the app already records.
- Range validation gate (`src/strategy/validation/`, `scripts/validate-ranges.ts`, `docs/validacao-ranges.md`): only families validated against an external reference (HRC first; GTO Wizard last resort) may be trained once `validation/config.json` has `"gate": true`. Rule per node: ≥95% of combos with the reference's main action and every divergence costing <0.05bb (0.02% pct) in our EV; per family: all compared nodes pass, minimum node count, and solver presets with ≤3% inconsistent actions. Gate ON since 25/10/2026 (Eduardo): only push/fold Nash chip EV (first-in shove and call, 14 HRC nodes, 99.7%) is validated; the preflop solver catalog (chip_25: RFI 91–98.5%, BB defense 80–83%) and team open charts 25bb (91–93%) failed against HRC 4.1 Classic. Resteal is its own family (`nash_resteal:*`, depends on the opener range). Decision: HRC becomes the range source for spots it can solve (Classic: ≤30bb, 50k nodes); our engine stays only where it matches HRC. Unvalidatable sources (reaction.ts reference, calibrated ICM, limp chart) never pass the gate. Why: players only see ranges that were checked against a commercial solver.
- HRC as range source (`scripts/import-hrc.py`, `public/solver/hrc/`): HRC "Export Strategies" (All Strategies, Limited depth 3, zip of node JSONs with per-hand frequencies and EVs) is converted to the catalog format (rfi/resp/opv3 + EVs, 9-max) as `hrc_<preset>`. `presetFor` prefers a loaded `hrc_<name>` over the engine preset, and it also replaces team charts in chip-EV opens. Family `hrc:<name>` is validated by definition (added by `validate-ranges.ts` from the HRC manifest). First file: hrc_chip_25 (HRC 4.1 Classic, MC-CFR CI<10, 256 postflop buckets, open 2bb, 3bet IP 2.5x/SB 2.9x/BB 3.4x, 4bet all-in, max 3 players in the hand). Why: the gate only allows validated ranges; HRC output is the reference itself.
- Resteal validation and opener prior (`scripts/hrc-nash-refs.py --resteal`, `scripts/import-hrc-opens.py`, `src/strategy/pushfold/hrc-opens.ts`, `validation/references/nash_resteal_chip_*`): HRC Enumerated trees with open 2bb (no flat of the open, closing flats off), 3bet/4bet all-in only, cold calls on, chip EV, 9-max equal stacks 12/15/20/25bb (the resteal buckets), CFR+ 4000 iterations (Fictitious Play left low-reach nodes unconverged even at 4300: HRC itself played −EV hands, e.g. opener calling T9s at −0.15bb). 8 nodes per stack (BB vs UTG, BTN vs LJ, SB vs HJ, BTN vs CO, BB vs CO, SB vs BTN, BB vs BTN, BB vs SB); node spec `{type:"nash", opener}`. Finding 26/10: our solver matches HRC when the opener holds HRC's own 2bb open range (BB vs UTG 15bb: 99.7%) but not with the old reference open ranges (too tight → resteal too tight, BB vs SB 65%), so chip-EV 9-max resteal now uses `HRC_OPENS` as the opener prior (`openerPrior(..., hrc=true)`, nearest stack); ICM/PKO/other table sizes keep the reference prior. Result 26/10: nash_resteal:chip_ev VALIDADO 32/32 (99.7%) after replacing the global three-way share (`share3`, one fitted beta) by a per-hand fit (`share3h`, `SHARE3_PARAMS` from `scripts/fit-share3.py` + `scripts/three-way-equity.c`: beta and offset per hand class, CV RMSE 0.66 vs 1.67 points); the misses were SB vs BTN, where the BTN overcalls 38% of its open and three-way pots dominate (exact Monte Carlo showed our EV off by ~0.06bb there).
